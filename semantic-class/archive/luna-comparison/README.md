# gpt-5.6-luna との比較と和集合

akunuki の意味分類表(名詞ごとに意味の中項目を並べた参照データ)を、どのモデルに作らせるのが最もよいかを測った記録である。同じ方針と同じ few-shot のまま、Haiku で作った表、gpt-5.6-luna で作った表、その 2 つを語ごとの和集合で合併した表の 3 つを比べた。

最もよいのは Haiku の表である。luna の表は、もとの分類語彙表から作った表との一致でも語の被覆でも Haiku を上回る。ところが検出器の成績は逆に下がる。抽象的な内容の段落に具体物の名詞が立つことを指摘する `concrete-noun-misfit` では、3 つのコーパスの合計で指摘が 735 件から 869 件へ 18% 増えた。そこから抜いた 30 件に妥当な指摘は 1 件もなかった。和集合の表は指摘が 702 件と最も少ないものの、妥当は 30 件中 1 件で、どちらも Haiku 単独に対する改良にならない。

## 前提条件

同梱の `configs/cfg-luna.toml` と `configs/cfg-union.toml` は、1 バイトも違わない。どちらも意味分類表を `reference/semantic-class-table.tsv` という相対パスで指す。luna の表と和集合の表の違いを持っていたのは、設定ファイルではなく、設定と並べて置いた `reference/` の中身である。閾値も設定ファイルからは読めない。`lint_v3.sh` が実行のたびに `abstract_ratio` の行を第 3 引数で上書きするためであり、スナップショットに残る 0.70 は掃引の最後の値で、採点の数字を出したときの 0.85 ではない。3 つの実行で変えたのは、表と閾値の 2 つだけである。

`concrete-noun-misfit` は、引けた分類がすべて生産物か自然物の部門にある語だけを具体物とみなす。抽象の部門の中項目が 1 つでも付けば、その語は具体物から外れる。

指摘を出した akunuki のバイナリの版は記録がない。`lint_v3.sh` は環境変数 `AKUNUKI_DIR` の下の `target/release/aku` をそのまま呼び、版を書き出していない。出力の JSON もパスと行と桁と語だけを持つ。

リポジトリに入っていないものは、3 つのコーパスと、設定と並べて置いた `reference/` である。コーパスは手元の Markdown へ差し替えれば lint 自体は動くが、件数は採点の数字と比べられない。分類は API を呼ぶため、API キーがあっても同じ表は再び出ない。一方、3 つの表は `../haiku-contract-iteration/` とこのフォルダに、指摘は `findings-*.json` に、当否の判定は `verdicts_v3.py` にある。表の統計と、採点・標本・推定は、この 3 つだけで同じ数字を再現できる。

指摘の当否は LLM による自動の判定で、人手の確認を経ていない。判定の基準は `../finding-verdicts/verdicts_v2.py` と同じである。定着していない転用や直訳のうち、現代の技術文書の読み手が引っかかる使い方だけを妥当とした。定着した語義と専門用語への指摘は、語の分類がどうであれ誤検出と数えている。突き合わせに使う判定済みの標本 170 件は、妥当と判定した 6 件と誤検出 164 件からなる。

この測定で見るのは適合率だけである。適合率とは、検出器が出した指摘のうち妥当だったものの割合であり、ここでは残った指摘から種 694 で無作為に抜いた 30 件を分母として数えた。検出器が指摘しなかった候補を見ていないため、指摘すべき箇所を見落とした件数(偽陰性)と、指摘すべきでない箇所を正しく指摘しなかった件数(真陰性)は測っていない。したがって、指摘すべきだったもののうち実際に指摘した割合である再現率は出せない。評価の枠組みは `../../eval/methodology.md` にある。

## 表の生成から採点までの手順

次のコマンドを上から順に実行した。ベンチマークの測定から表の生成と和集合の合併を経て、lint と採点までを行っている。実行には venv と、`OPENAI_MODEL` を含む `~/.env` が要る。分類は API を呼ぶため、同じ表が再び出る保証はない。和集合の合併では API を呼ばず、生成済みの分類だけから表を作った。

```
# ベンチマーク 200 語を luna で測る
python exp_bench_v3.py OPENAI_MODEL exp_bench_v3_luna.json

# コーパスの見出し語 7,743 語を luna で分類して表を作る
python build_table_v3.py OPENAI_MODEL classifier_v3_43 luna-v3

# 2 つの判定を語ごとの和集合で合併する(API は呼ばない)
python merge_union_v3.py

# 3 つのコーパスへ lint を掛ける(閾値 0.85 と 0.70)
bash lint_v3.sh cfg-luna  luna  0.85
bash lint_v3.sh cfg-union union 0.85

# 採点・標本・推定
python score_v3.py luna 0.85       > score-v3-luna-085.txt
python sample_v3.py findings-luna-0.85.json > sample-v3-luna-085.txt
python estimate_v3.py "luna 0.85" 0 30 869
python table_stats_v3.py luna-v3-semantic-class-table.tsv
```

## 生成元と条件ごとの指摘と適合率

生成元と方針、閾値、後段の除外の規則を変えた条件ごとに、指摘の件数と適合率を並べる。閾値は `abstract_ratio` の値である。

| 生成元と条件 | 指摘の総数 | 妥当な 6 件の保持 | 判定済みの誤検出 164 件の消滅 | 標本の適合率 | 妥当と推定した件数 |
|---|---|---|---|---|---|
| 分類語彙表由来 | 1,314 | 5/6 | — | 6.4%(層別 170 件) | 85 |
| 日本語 WordNet 由来 | 1,351 | 3/6 | — | 4.0%(層別 170 件) | 54 |
| Haiku 訂正後の方針 + 0.85 | 735 | 3/6 | 85.4% | 6.7%(2/30) | 49 |
| luna 訂正後の方針 + 0.85 | 869 | 2/6 | 82.3% | 0.0%(0/30) | 0 |
| luna 訂正後の方針 + 0.70 | 1,609 | 2/6 | 70.7% | — | — |
| Haiku ∪ luna + 0.85 | 702 | 2/6 | 83.5% | 3.3%(1/30) | 23 |
| Haiku ∪ luna + 0.70 | 1,016 | 2/6 | 79.3% | — | — |
| Haiku 44 分類 + 中項目 48 の除外 + 0.85 | 202 | 2/6 | 96.3% | 3.3%(1/30) | 7 |
| Haiku 訂正後の方針 + `comp` 除外 + 0.85 | 561 | 3/6 | 88.4% | 3.3%(1/30) | 19 |

分類語彙表由来の表と日本語 WordNet 由来の表で消滅の列が空なのは、判定済みの標本をこの 2 つから抜いたためである。この 2 行の適合率は、`../finding-verdicts/` の層別の標本 170 件から推定した値であり、他の行の 30 件とは分母が違う。標本の適合率の 95% 信頼区間は、0/30 が 0.0%〜11.4%、1/30 が 0.6%〜16.7%、2/30 が 1.8%〜21.3% である。区間はすべて重なるため、適合率の順位は点推定のもので、統計としては確定しない。

中項目 48 の除外の行と `comp` 除外の行は、表そのものではなく、生成した表に後段の除外の規則を足した場合のシミュレーションである。無形の人工物を受ける中項目 48 を足す案と、対訳表の分野タグ `comp` で代用する案は、どちらも誤検出をよく減らす一方で妥当な指摘も道連れにし、適合率を上げなかった。この 2 つの測定の記録は `../software-class-estimate/README.md` にある。

## luna の比較の計測

### 実験の条件

生成の方針の文言と few-shot の 26 語は、Haiku の測定のまま使った。用例の添え方とバッチの大きさ、並列数、混ぜる種も変えていない。変えたのはモデル名だけである。

### ベンチマーク 200 語の一致

種 694 で抜いた同じ 200 語で、分類語彙表由来の表との一致を測った。この一致は参考値である。

| 指標 | Haiku | luna |
|---|---|---|
| 中項目の集合の一致(コーパス) | 31.0% | 39.0% |
| 中項目の集合の一致(無作為) | 31.0% | 44.0% |
| 部門の集合の一致(コーパス) | 67.0% | 70.0% |
| 部門の集合の一致(無作為) | 66.0% | 74.0% |
| 具体物の条件の一致(コーパス) | 94.0% | 95.0% |
| 具体物の条件の一致(無作為) | 91.0% | 91.0% |

luna は 6 つの指標のうち 5 つで Haiku を上回った。分類語彙表由来の表との一致だけを見れば、luna の方がよい表を作る。

### 生成した表

luna はコーパスの見出し語 7,743 語のうち 7,739 語を分類し、失敗したバッチは 0 だった。表の行は 7,740 である。Haiku の訂正後の方針の表は 7,693 語を覆うので、被覆では luna が上回る。分類語彙表由来の表と重なる 5,861 語で測ると、部門の集合の一致は 64.2%、具体物の条件の一致は 92.6% である。Haiku の 59.8% と 91.6% をどちらも上回る。

### 3 コーパスでの指摘と採点

閾値 0.85 で 869 件、0.70 で 1,609 件だった。同じ条件の Haiku は 735 件だったので、表の一致がよいのに指摘は 18% 増えた。

妥当な 6 件のうち保持したのは `ボード` と `バケット` の 2 件で、Haiku の表が保持した `野生` を落とした。判定済みの誤検出 164 件のうち消えたのは 135 件、82.3% で、Haiku の 85.4% を下回った。残る 869 件から種 694 で 30 件を抜いて当否を見たところ、妥当は 1 件もなかった。抜いた 30 件は `製`・`タグ`・`トークン`・`ブラウザ`・`証明書`・`端末` のように、どれも定着した専門用語か普通の日本語の用法だった。

### 中項目を絞る癖が指摘を増やす仕組み

luna は中項目の一覧を Haiku より短く作る。`アカウント` は、luna が `物品` の 40 だけを挙げるのに対し、Haiku は `金銭` の 37 と 40 の両方を挙げる。`トークン` は luna が 40 だけ、Haiku は `言語活動` の 31 と 40 である。`アプリ` は luna が `道具・機械` の 45 だけ、Haiku は 31 と 40 である。

中項目を絞れば抽象の部門の中項目が付く機会も減るので、具体物とみなす語は増える。実際、具体物だけを持つ語の割合は、Haiku の 14.2% に対して luna が 15.5% である。

`野生` を落とすのも同じ仕組みの裏返しである。luna はこの語に様相の 13 だけを与える。中項目が抽象の部門に入るため、語の側で具体物から外れ、指摘が出ない。分類語彙表由来の表との一致を測る物差しでは luna の方が正しく、検出器の物差しでは luna の方が誤る。

## luna についての所見

表の質と検出器の成績はつながらない。luna は分類語彙表由来の表との一致でも被覆でも Haiku を上回るのに、指摘は増え、妥当な指摘を落とし、標本には妥当が 1 件もなかった。この検出器が読むのは分類の正しさではなく、抽象の部門の中項目が 1 つでも付いているかだけである。表の一致率が高くても、指摘の成績が上がるとは限らない。

## 和集合の計測

### 合併した表

片方にしか載らない語には、その片方の分類をそのまま採った。行は 7,744 で、コーパスの見出し語 7,743 語をすべて覆う。被覆はこれまでで最も広い。

ところが、両方に載る 7,689 語のうち中項目の集合が一致するのは 3,720 語、48.4% でしかない。つまり半分以上の語で 2 つのモデルの答えが割れる。合併で中項目の数が両方より増える語は 1,938 語である。分類語彙表由来の表と重なる 5,862 語で測ると部門の集合の一致は 56.7% で、Haiku の 59.8% と luna の 64.2% のどちらも下回る。中項目を足すほどこの表の集合とは離れるため、これは仕組みから予想できる。

### 和集合の機構

和集合はどちらのモデルの中項目も採るため、片方でも抽象の部門の中項目を挙げた語は具体物から外れる。

数で確かめられる。両方に載る 7,689 語のうち具体物だけを持つのは、Haiku で 1,089 語、luna で 1,182 語である。ところが和集合では 883 語しかなく、この 883 語は 2 つの集合の積そのものである。片方だけが具体物とした 505 語が、和集合では除外の側へ回る。

つまり和集合は、中項目の和集合を取ることによって、具体物とみなす語の積集合を取る。表としては最も中項目が多く、検出器としては最も指摘が少なくなる。指摘は 0.85 で 702 件と、これまで測った表の中で最も少ない。

`野生` はこの機構で消える。Haiku はこの語に土地の利用の `47` と生物の `53` を与え、luna は様相の `13` を与える。和集合は `[13, 47, 53]` になり、抽象の部門を含むため語の側で具体物から外れる。`野生` は妥当な 6 件のうち最も明快な 1 件で、「野生での悪用」は in the wild の直訳である。日本語の脆弱性情報なら、実際の環境での悪用と書く。落とす原因は luna の分類が誤っていることだが、和集合はどちらが誤っているかを判定できず、常に除外の側へ倒れる。

残る `ボード` と `バケット` が生き延びるのは、2 つのモデルがどちらも具体物だけを与えるためである。保持は 2/6 で、luna 単独と同じになる。

## 和集合についての所見

第 1 に、和集合は誤検出を減らす向きに働く。702 件は Haiku の 735 件より 4.5% 少なく、luna の 869 件より 19% 少ない。2 つのモデルが割れた語をすべて除外するため、これも仕組みから予想できる。

第 2 に、それでも `concrete-noun-misfit` の指摘の適合率は上がらない。3.3% で、Haiku の 6.7% の半分の点推定である。区間は重なるため差は確定しないが、少なくとも和集合でこの値が上がる証拠は得られない。妥当と推定した件数も 49 件から 23 件へ落ちる。

第 3 に、和集合は誤りの向きを 1 方向に固定する。2 つのモデルが割れたとき、和集合は必ず「抽象の部門の中項目がある」と読み、この検出器ではそれが必ず「指摘しない」に倒れる。そのため和集合が減らすのは誤検出だけではなく、妥当な指摘も同じ向きで減る。判定済みの誤検出の消滅は 83.5% で、Haiku の 85.4% を下回る。それでいて妥当の保持も 3 件から 2 件へ下がるのは、この向きの固定による。

第 4 に、2 つのモデルの答えは半分以上の語で割れる。一致は 48.4% で、どちらを信じるかを決める根拠は表の中にない。測った範囲では、和集合は Haiku 単独に対する改良にならない。

## 結論

「どの言語資源で表を作るか」という問いには、測定の範囲で答えが出ている。Haiku の訂正後の方針が最もよく、luna は劣り、日本語 WordNet はさらに劣る。ただし最良の表でも、`concrete-noun-misfit` の指摘の適合率は 6.7% にとどまり、表の選択ではこの値が動かない。

ここまでに測った組み合わせでは、この検出器の指摘は 9 割以上が誤検出である。生成元と方針、閾値、除外の規則のどれを変えてもこの比率は動かず、妥当な指摘は裾に 1 件ずつしか現れず、頻度の上位は常に定着した専門用語で占められる。
