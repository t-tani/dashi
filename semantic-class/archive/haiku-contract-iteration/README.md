# Haiku の生成の方針の反復

どの語義を挙げよという指示を書き直しながら、`concrete-noun-misfit` の指摘がどう変わるかを測った記録である。この検出器は、抽象的な語の多い段落に具体物の名詞が単独で立っている箇所を指摘し、名詞ごとに分類語彙表の中項目を割り当てた意味分類表を引く。この表は Haiku に作らせた。分類語彙表は名詞の意味を 5 つの部門に分け、部門の下を全 43 の中項目に分ける。

指示の書き直しは誤検出を減らすが、指摘の質は変えない。定着した転用の語義まで挙げよという訂正後の指示で、判定済みの誤検出 164 件のうち 140 件(85.4%)が消えた。ところが残った 735 件から 30 件を抜くと、直すべき文を指した指摘は 2 件だけで、適合率は 6.7% にとどまる。分類語彙表由来の表の 6.4% と区別がつかない。

この実験は 2 段で進めた。まず表の生成を LLM に移せるかを見て、次に、どの語義を挙げよと指示すれば定着した専門用語への誤検出が減るかを試した。生成の方針の全文は「生成の方針の訂正」に、閾値の選び方は「閾値の再校正」にある。

当否は自動の判定(LLM)で、人手の確認を経ていない。この測定が見ているのは適合率だけである。適合率は、検出器が出した指摘のうち妥当だったものの割合を指す。検出器が指摘しなかった候補を見ていないため、見逃した指摘である偽陰性も、正しく指摘しなかった箇所である真陰性も数えていない。指摘すべきもののうち実際に指摘した割合である再現率も、同じ理由で出せない。評価の枠組みは `../../eval/methodology.md` にある。

## 前提条件

比較は 2 つある。few-shot の比較では、ベンチマークの 200 語と種 694 とモデルをそろえ、変えたのは指示だけである。すなわち `classifier-v1.py` と `demos-v1.py` の実例 23 語から、`target.py` の実例 26 語への差である。lint の比較では、同梱した `cfg-haiku.toml` と `cfg-haiku2.toml` の差は `abstract_ratio` の 1 か所だけである。値は 0.7 と 0.90 で、ほかのキーは 1 つも違わない。表の差は設定ファイルの外にある。

同梱の `cfg-haiku2.toml` は掃引の最後の 0.90 のままである。「採点(訂正後の方針 + 閾値 0.85)」の 735 件は `abstract_ratio` を 0.85 にして取ったので、同梱の設定をそのまま使うと 392 件になる。どちらの設定も、設定のパスからの相対で `reference/semantic-class-table.tsv` を読む。その symlink はリポジトリに入っていないので、このフォルダの表から `reference/` を自分で組む。実験では `cfg-haiku.toml` を語義を絞る方針の表へ、`cfg-haiku2.toml` を訂正後の方針の表へ向けた。

指摘を出した akunuki のバイナリの版は記録がない。使ったモデルも入力データの表にはなく、生成した表の冒頭のコメントから `claude-haiku-4-5-20251001` と辿れるだけである。

表の生成には `ANTHROPIC_BASE_URL`・`ANTHROPIC_API_TOKEN`・`ANTHROPIC_MODEL` を持つ `~/.env` が要る。用例を取る `corpus-text.txt` は手元にない。lint を掛けた評価コーパスと docs A と docs B も同じである。一方、生成した 2 つの表とベンチマークの 200 語と判定済みの標本はリポジトリにある。表を作り直さず、既存の表で手元のコーパスへ lint を掛け直すところまではできるが、件数はこの記録と一致しない。

## 手順

再現には venv と、`ANTHROPIC_BASE_URL`・`ANTHROPIC_API_TOKEN`・`ANTHROPIC_MODEL` を持つ `~/.env` が要る。分類は API を呼ぶため、同じ表が出る保証はない。ただし、バッチの組み方を固定すれば温度 0 の判定は再現し、その測定は `../batch-effect/` にある。実行したのは次のコマンドである。

```
# ベンチマーク 200 語(few-shot 無し / 語義を絞る方針 / 訂正後の方針)
python exp_small.py
python exp_fewshot.py
python exp_fewshot_v2.py

# コーパスの見出し語 7,743 語を分類して表を作る
python build_haiku_table.py       # 語義を絞る方針
python build_haiku_table_v2.py    # 訂正後の方針

# 3 つのコーパスへ lint を掛ける
aku lint --format json --config cfg-haiku2/config.toml --dict .aku/dict <コーパス> > <コーパス>-haiku2.json

# 閾値を 0.50 から 0.90 まで 0.05 刻みで掃引する
bash ../luna-comparison/lint_v3.sh

# 判定済みの標本で採点し、適合率を推定する
python score_haiku.py    > score-haiku.txt
python estimate_haiku.py > estimate-haiku.txt
```

## 語義を絞る方針の採点

Haiku に意味の中項目を答えさせて意味分類表を作り、判定済みの指摘 140 件で採点した。この採点は、定着した語義と専門用語への指摘を誤検出と数えない旧い基準で取った。改訂後の基準で数え直した値は「採点(訂正後の方針 + 閾値 0.85)」の表にある。Haiku 表は WordNet 由来の表よりはっきりよくなるが、分類語彙表由来の表には届かない。判定済みの誤検出 44 件のうち Haiku 表が再現するのは 4.5% にとどまる一方で、分類語彙表由来の表が出した妥当な指摘 64 件の 58% を落とす。指摘の総数は 2 倍に増え、推定した適合率は 48.1% で、分類語彙表由来の表の 79.0% には届かない。

## 語義を絞る方針の few-shot

誤りの型を 5 つ狙って、実例を 23 語ぶん書いた。狙う型は国と地域を 26 へ入れること、人と組織を表す語義を落とさないこと、比喩でだけ生まれる語義を足さないことである。残る 2 つは、経済と金銭の 37 を見落とさないことと、方法の 30 を見落とさないことである。実例は 5 つの組に分け、`dspy.Example` として predictor の demos に積んだ。用例を添えた形と添えない形の両方を見せた。

実例の語も中項目も、43 中項目の定義文だけを見て決めた。ベンチマークの 200 語と 1 語も重ならないことは機械で照合した。測り直しには種 694 の同じ 200 語を使った。次の表の各セルは、矢印の左が few-shot 無し、右が few-shot ありの値である。

| 指標 | コーパス 100 語 | 無作為 100 語 |
|---|---|---|
| 中項目の集合の一致 | 23.0% → 39.0% | 30.0% → 45.0% |
| 中項目の交わりあり | 64.0% → 53.0% | 60.0% → 55.0% |
| 部門の集合の一致 | 65.0% → 66.0% | 64.0% → 77.0% |
| 具体物の条件の一致 | 91.0% → 89.0% | 89.0% → 92.0% |
| 抽象を含むかの一致 | 90.0% → 85.0% | 84.0% → 92.0% |

中項目の一致は両方で 15 ポイント上がった。無作為の 100 語では部門の一致も 13 ポイント上がる。一方でコーパスの 100 語は、具体物の条件と抽象を含むかがわずかに下がる。原因は、実例が語義の数を絞る向きに効くことである。交わりありが下がっていることがその跡で、比喩の語義を足さない実例が、計算機の文脈で要る抽象の語義まで削っている。

## 語義を絞る方針での表の生成

コーパスに現れた見出し語の一覧を、`../wordnet-mapping/` と同じ方法で作り直した。分類語彙表由来の表と WordNet 由来の表の見出し語を合わせた集合を、評価コーパスの本文に対して部分文字列として走査する方法である。件数は当時と同じ 7,743 語である。

この全語を few-shot 込みの分類器へ渡した。20 語ずつのバッチにし、`ThreadPoolExecutor` で 8 並列にした。バッチの中身は種 694 で混ぜてある。並びのままだとラテン文字の断片だけのバッチができ、モデルが空の配列を返すためである。コーパスから用例を取れた語は 4,984 語で、その語には用例を添えた。

388 バッチのうち 16 バッチが 3 回とも失敗した。失敗はどれも同じ形で、モデルが空の配列を返し、1 件以上という検証に落ちる。結果として 7,136 語が分類でき、同じ数の行を持つ表になった。このうちコーパスの見出し語と一致するのは 7,134 語である。分類番号は `1.mm00` の形で、mm が中項目の 2 桁、小数点以下第 3 位と第 4 位は 0 で埋める。読み込み側は整数部が 1 で小数点以下が 4 桁の形を求めるため、この形で受かる。表の冒頭には、モデル名と生成の日と方式を注記に書いた。

## 語義を絞る方針の表の一致

コーパスの 7,743 語のうち、分類語彙表由来の表に載るのは 5,862 語、WordNet 由来の表は 6,055 語、Haiku 表は 7,134 語である。被覆は Haiku が最も広い。

分類語彙表由来の表と重なる語で測った一致を、Haiku 表と WordNet 由来の表で比べる。

| 指標 | Haiku 表(5,458 語) | WordNet 由来(4,174 語) |
|---|---|---|
| 部門の集合の一致 | 64.8% | 43.2% |
| 部門の交わりあり | 80.2% | 83.5% |
| 具体物の条件の一致 | 90.3% | 91.0% |
| 抽象を含むかの一致 | 87.9% | 88.0% |

部門の集合の一致は 21 ポイント上回る。ところが検出器が実際に使う具体物の条件は、ほとんど差がない。表の質は上がるのに、この検出器の判定に効く部分は動かない。

## 判定済み 140 件での採点

**(a) 妥当な指摘の保持。** 分類語彙表由来の表だけが出す指摘のうち妥当と判定した 52 件では、Haiku 表が保持するのは 22 件で 42.3% である。両方が出す指摘のうち妥当と判定した 12 件では 5 件で 41.7% である。合わせると 64 件中 27 件、42.2% しか残らない。落ちる語には `標的`、`鍵`、`キー`、`タグ`、`バイパス`、`背景`、`踏み台`、`炎上`、`導線`、`ノイズ` が並ぶ。

**(b) 誤検出の再現。** 誤検出と判定した 44 件のうち、Haiku 表が再現するのは 2 件で 4.5% にとどまり、再現する語は `インターネット` だけである。したがって WordNet 由来の表の誤検出はほぼ止まっている。

**(c) Haiku 表だけが出す指摘。** 分類語彙表由来の表にも WordNet 由来の表にもない指摘が 1,795 件あり、指摘に出た語の種類は 252 である。多い順に `ファイル` 100 件、`ツール` 62 件、`スクリプト` 57 件、`エージェント` 55 件、`システム` 47 件と続く。この 1,795 件から種 694 で 30 件を抜いて当否を見た。妥当 13 件・誤検出 16 件・表の当否を測れない 1 件で、適合率は 43.3%(95% 信頼区間 27.4%〜60.8%)である。妥当としたのは `ファイル`、`ページ`、`スクリプト`、`パッケージ`、`木`(Merkle 木)、`コレクション` のように、具体物を指す語を計算機の事柄へ写したものである。誤検出としたのは `システム`、`プログラム`、`アプリ`、`版`、`拡張子` のように、もともと具体物を指さない語である。

**(d) 適合率の推定。** Haiku 表の指摘を、どの表と重なるかで 4 つの層に分けた。層ごとに標本を抜いて適合率を出し、層の件数で重み付けして全体の適合率を推定する。

| 層 | 件数 | 標本の適合率 | 妥当の概算 |
|---|---|---|---|
| 分類語彙表由来だけが出す指摘と重なる | 313 | 52/60 = 86.7% | 271 |
| WordNet 由来だけが出す指摘と重なる | 259 | 14/60 = 23.3% | 60 |
| 分類語彙表由来と WordNet 由来の両方と重なる | 241 | 12/20 = 60.0% | 145 |
| Haiku 表だけが出す | 1,795 | 13/30 = 43.3% | 778 |

合計すると、2,608 件のうち妥当はおよそ 1,254 件で 48.1% である。分類語彙表由来の表は 1,314 件のうちおよそ 1,038 件で 79.0% である。適合率では 31 ポイント負ける。ただし妥当な指摘の絶対数では 1,254 件と 1,038 件で Haiku 表が上回る。妥当な指摘を多く拾う代わりに、適合率を下げた形である。

## 系統的な問題

第 1 に、カタカナで書く計算機の語を具体物へ寄せる。Haiku 表にあって分類語彙表由来の表にないコーパスの語は 1,676 語あり、そのうち 529 語(31.6%)を具体物だけに分類している。529 語のうち 383 語がカタカナだけの語である。`ファイル`、`ツール`、`スクリプト`、`エージェント` はどれもこの型で、新規の指摘の上位を占める。ソフトウェアや抽象的な仕組みを指す語を、`道具・機械` や `物品` の中項目へ入れている。

第 2 に、具体物が増えると段落の判定が壊れる。この検出器は、関係か活動の部門の語が段落の 7 割を超えたときだけ報告する。具体物の語が増えれば、この比率は下がる。だから分類語彙表由来の表の妥当な指摘の 58% が消える。`鍵` は Haiku 表でも生産物の中項目だけを持つのに、指摘が出ない。語の分類ではなく、段落が閾値を割るためである。閾値はその表の具体物の密度に合わせて置かれているため、表を替えると同じ閾値が同じ意味を持たない。

第 3 に、頻度の高い語を 1 語外すと大きく効く。`標的` を事柄の 10 に分類するため、101 件の妥当な指摘が語の側で消える。1 語の判断が指摘の 8% を動かす。

## 語義を絞る方針のまとめ

Haiku 表は WordNet 由来の表より明確にすぐれる。部門の集合の一致は 43.2% から 64.8% へ上がり、誤検出の再現は 4.5% に収まり、被覆は 7,134 語で最も広い。それでも分類語彙表由来の表の適合率には届かない。届かない理由は表の質だけではなく、段落の閾値がその表の密度に合わせてあることと、計算機の語の扱いが決まっていないことにある。

この採点は、段落の閾値を分類語彙表由来の表の密度に合わせたまま行った。閾値を Haiku 表の密度へ振り直したときの適合率と、カタカナの計算機の語を具体物とみなす範囲を変えたときの適合率は、どちらも測っていない。

## 生成の方針の訂正

表の生成の方針を訂正し、分類をやり直して採点した。訂正前の文言で取った表とベンチマークは破棄し、数字はすべて訂正後の文言で取り直したものである。

訂正後の文言では、語義として挙げるのは現代の日本語で日常的に使われると広く認められるものだけである。比喩や転用に由来する語義も、辞書に載る程度に定着していれば挙げる。攻撃の対象を指す `標的` がこれに当たる。挙げないのは 3 つで、まだ定着していない直訳や転用、特定の分野や集団の中でしか通じない用法、文学的・修辞的な言い回しにだけ現れる語義である。迷ったら挙げない側に倒す。

訂正の前の文言は「定着して持つ語義は比喩・転用由来でもすべて挙げる」だった。この形は語義の列挙を膨らませ、周辺的な比喩語義まで付いて検出器の除外が効きすぎる。挙げない側の誤りは指摘として表に出るため、語ごとに分類を直せる。挙げる側の誤りは指摘を出さずに消えるため、見つける機会そのものがない。

文言は 3 か所へ入れた。Signature の指示文、few-shot の理由を書いたファイル、生成した表の冒頭コメントである。few-shot は 26 語で、うち 8 語が「辞書に載る程度に定着した転用の語義を挙げる」側、3 語が「挙げない」側である。挙げない側は直訳と比喩と修辞を 1 つずつ受け持つ。分類語彙表の行を写さない規律は従来どおり守り、ベンチマークの 200 語とも採点に使う 6 語とも重ならないことを機械で照合した。

中項目の一致は落ちるが、検出器が実際に使う具体物の条件はコーパス側で 94.0% と、3 つの中で最も高い。

## 訂正後の方針で生成した表

コーパスの見出し語 7,743 語のうち 7,693 語を分類できた。被覆は 3 つの表の中で最も広い。分類語彙表由来の表は 5,862 語、WordNet 由来の表は 6,055 語である。

分類語彙表由来の表と重なる 5,846 語で測ると、部門の集合の一致は 59.8%、具体物の条件の一致は 91.6% である。語義を絞る方針の表は同じ指標で 64.8% と 90.3% である。集合の一致が下がって具体物の条件が上がるのは、訂正後の方針が定着した転用の語義を足すぶん、その表と語義の数が食い違うためである。具体物だけを持つ語の割合は 18.9% から 14.2% へ下がる。

## 閾値の再校正

`abstract_ratio` を 0.50 から 0.90 まで 0.05 刻みで掃引した。

| 閾値 | 指摘の総数 | 妥当 6 件の保持 |
|---|---|---|
| 0.50 | 1,259 | 3 |
| 0.60 | 1,253 | 3 |
| 0.70 | 1,206 | 3 |
| 0.80 | 975 | 3 |
| 0.85 | 735 | 3 |
| 0.90 | 392 | 3 |

保持は全域で 3 のまま動かない。だから保持では閾値を選べず、動くのは総数だけである。

保持の上限は 6 ではなく 4 である。`原子` と `導線` は表の語彙の外にあり、どの閾値でも出せない。表が覆うのは評価コーパス 300 ファイルに現れた語だけで、この 2 語は別のコーパスにしか現れないためである。`窓` は表が保守の窓を指す時間の語義を与えるため、除外される。到達できる 4 件のうち 3 件を保持する。

閾値は 0.85 を選んだ。理由は 2 つある。第 1 に、既定の 0.70 に対して指摘を 39% 減らしながら、判定済みの妥当な指摘を 1 件も落とさない。第 2 に、0.90 は総数をさらに半分にするが、分類が引けた名詞の 10 語中 9 語が抽象でなければ段落が成立しない条件になる。短い段落では 1 語の増減で判定が反転するため、壊れやすい端は避けた。

## 採点(訂正後の方針 + 閾値 0.85)

判定基準は改訂後のものである。定着した語義と専門用語への指摘は、語の分類がどうであれ誤検出と数えた。

**(a) 妥当な指摘の保持。** 6 件のうち 3 件、すなわち `野生`・`ボード`・`バケット` を保持する。到達できる 4 件を分母にすれば 3 件である。

**(b) 判定済みの誤検出の消滅。** 判定済みの誤検出 164 件のうち 140 件、85.4% が消える。一方、閾値 0.70 では 125 件で 76.2% にとどまる。残る語は `シェル` 3 件、`機器` 3 件、`製品` 3 件などで、いずれも少数である。誤検出の実例として示された `標的`、`パッチ`、`鍵`、`ファイル` の型は全件消える。

**(c) 残った指摘。** 735 件で、語の種類は 182 である。ここから種 694 で 30 件を抜いて当否を見た。妥当 2 件・誤検出 28 件で、適合率は 6.7%(95% 信頼区間 1.8%〜21.3%)である。妥当としたのは「ベンダー消滅はシステムの死ではなく」の `死` と、検査対象の文書自身が退ける語として挙げている `機械` の 2 件で、どちらも境界の判定である。

**(d) 適合率の推定。** 735 件のうち妥当はおよそ 49 件で、適合率は 6.7% である。4 つの表の適合率と妥当の概算を並べる。

| 表 | 指摘の総数 | 適合率 | 妥当の概算 |
|---|---|---|---|
| 分類語彙表由来 | 1,314 | 6.4% | 85 |
| WordNet 由来 | 1,351 | 4.0% | 54 |
| Haiku(語義を絞る方針) | 2,608 | 1.7% | 44 |
| Haiku(訂正後の方針 + 閾値 0.85) | 735 | 6.7% | 49 |

## 訂正後の方針の所見

第 1 に、訂正後の方針は狙いどおりに働く。定着した専門用語への指摘の 85% が消える。few-shot に入れた 8 語が消えるのは仕組み上あたりまえだが、実例にない語にも効いている。`システム` は機関・組織の語義を得て除外され、`プログラム` は言語活動と創作の語義だけになる。方針は実例の外へ一般化している。

第 2 に、それでも `concrete-noun-misfit` の指摘の適合率は分類語彙表由来の表と区別がつかない。6.7% と 6.4% で、標本の信頼区間は大きく重なる。変わるのは量である。指摘は 1,314 件から 735 件へ 44% 減り、誤検出の絶対量は減る。ただし妥当な指摘の絶対数も 85 件から 49 件へ落ちる。

第 3 に、残る誤検出はカタカナで書く計算機の語に集中したままである。`パッケージ` 30 件、`モジュール` 28 件、`ブラウザ` 28 件、`コンポーネント` 18 件が上位を占める。分類器はこれらを `物品` か `道具・機械` に入れる。方針は定着した語義を挙げよと言うが、`ブラウザ` や `パッケージ` に与えるべき抽象の語義が 43 中項目のどれなのかを決められない。ソフトウェアや仕組みを指す語義を受ける中項目が、43 中項目にないためである。

第 4 に、閾値は誤検出の量を絞るだけで、種類を変えない。0.70 から 0.85 で総数は 39% 減るが、妥当の保持も残る誤検出の型も動かない。閾値の校正では、この検出器の適合率は上がらない。

## 測定の範囲

動かしたのは生成の方針の文言と `abstract_ratio` の閾値だけである。43 中項目と、カタカナで書く計算機の語を検出器の対象に含めるかどうかは動かしていない。残る誤検出はその 2 つに掛かるが、掛かり方の大きさは測っていない。
