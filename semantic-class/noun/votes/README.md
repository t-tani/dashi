# 名詞の判定

名詞に意味の区分を与えるモデルの判定を、モデルごとに 1 つの JSONL で置きます。1 行が 1 語です。行のフィールドの意味は `../../pipeline/votes.py` の冒頭にあります。`manifest.json` は生成の来歴です。方針の全文と 43 中項目の一覧のほか、few-shot のバージョンと DSPy のバージョン、母集団の作り方と生成コマンドを持ちます。

## ファイル一覧

このディレクトリに置くファイルは次のとおりです。

| ファイル | 中身 |
|---|---|
| `<モデル>.jsonl` | 全語を対象にした 1 回目のパスの判定(種 694) |
| `<モデル>-s<種>.jsonl` | 日常語の部分集合を対象にした 2 回目と 3 回目のパスの判定(種 1002 と 1003) |
| `final/<モデル>.jsonl` | 語ごとに確定した中項目 |
| `manifest.json` | 生成の来歴と条件 |
| `run-*.log` | git が追跡しない走行のログ |
| `failed-*.json` | git が追跡しない失敗したバッチ |

パスごとにファイルを分けているのは、冪等な再実行が判定済みの語を飛ばす作りだからです。同じファイルに混ぜると、2 回目のパスの判定が飛ばされます。

## 判定の重ね方と確定

バッチの組み方が判定を動かすので、日常的に使われる語には判定を重ねます。全語に 1 回の判定を取ったうえで、`tier` が `corpus` の語と `jmdict_priority` が true の語の和集合(`../inputs/daily-subset.txt`)に、さらに 2 回の判定を足します。パスごとにバッチの組み方の種を変えるのは、温度 0 ではバッチを固定すると同じ判定が出るからです。判定の独立性は、バッチの組み方の違いだけから来ます。根拠の測定は `../../archive/batch-effect/` にあります。

確定値は `../../pipeline/finalize.py` が 2 つの規則で決めます。2 パス以上に現れた語では 2 パス以上が挙げた中項目だけを採り、1 パスにしか現れない裾の語ではその 1 回の判定をそのまま採ります。どちらの規則で決めたかは、確定値の `votes` と `rule` のフィールドで区別できます。一方、どの中項目も 2 回の判定に届かない語は確定させず、確定値にも `../semantic-class-table.tsv` にも載せません。分類を引けない語を検出器は指摘しないので、揺れた分類で指摘を出すより、載せない方が安全側だからです。落とした語と、2 回の判定に届かず落ちた中項目は、`../review/` に残します。

## 生成の方針のバージョン

`contract` のフィールドは、生成の方針のバージョンの識別子を持ちます。`../target.py` の指示文を書き換えたら、`../../pipeline/votes.py` の `CONTRACT` を上げてください。既存の行は書かれたときのバージョンを持ち続けるので、どの方針で出した判定かを行ごとに追えます。

バージョンごとの方針は次のとおりです。

| バージョン | 生成の方針 |
|---|---|
| `v2-corrected` | 定着した語義だけを挙げ、特定の文脈や界隈でしか通じない用法は挙げない |
| `v3-reworded` | 定着した語義だけを挙げ、特定の分野や集団の中でしか通じない用法は挙げない |

2 つのバージョンの違いは語の言い換えだけで、語義の判断基準は同じです。だから判定の取り直しは要らず、この判定の行は `v2-corrected` のままです。
