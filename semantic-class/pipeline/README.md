# 意味分類表の生成スクリプト

名詞と動詞の意味分類表は、`pipeline/` の共通のスクリプトで生成します。成果物ごとのコマンドと引数は `../noun/README.md` と `../verb/README.md` にあります。

## 準備

依存は uv で管理しています。定義はリポジトリ直下の `pyproject.toml` と `uv.lock` にあります。 uv が無ければ、先に入れてください。

```
curl -LsSf https://astral.sh/uv/install.sh | sh
```

次に依存を取り込みます。`.venv` はリポジトリ直下にでき、バージョンは `uv.lock` で固定しています。

```
uv sync
```

判定は LLM のゲートウェイを呼ぶので、`~/.env` に次の変数が必要です。値は dashi には入っていません。`OPENAI_MODEL` が要るのは、2 つのモデルで判定を取る場合だけです。

| 変数 | 用途 |
|---|---|
| `LLM_BASE_URL` | ゲートウェイの URL |
| `LLM_API_KEY` | ゲートウェイの API キー |
| `ANTHROPIC_MODEL` | Claude 側のモデル名 |
| `OPENAI_MODEL` | もう一方のモデル名 |

JMdict の XML(`JMdict_e.xml`)も必要です。`http://ftp.edrdg.org/pub/Nihongo/JMdict_e.gz` から取得して展開してください。用例を添えたい場合は、語が現れる本文を 1 つのテキストにまとめたものを別に用意してください。用例が無くても動きます。

## 生成の流れ

`semantic-class/` の中で、`uv run python pipeline/<スクリプト>` の形でスクリプトを実行してください。どのスクリプトも `--target` で成果物のフォルダを受け取り、そこにある `target.py` から分類対象の定義を読みます。定義が持つのは、指示文、few-shot の実例、分類番号の規約、採る品詞です。名詞と動詞で違うのはこの定義だけで、工程は変わりません。

最初に `headwords.py` が、JMdict から分類にかける語の母集団を作ります。次に `run_votes.py` が、母集団の語を 20 語ずつのバッチでモデルへ渡し、判定を JSONL へ追記します。

バッチの組み方の種を変えて母集団を通し直すと、判定を重ねられます。この 1 巡がパスです。重ねるのは、バッチの組み方が判定を動かすからです。温度 0 ではバッチを固定すると同じ判定が出るので、判定の独立性はバッチの組み方の違いだけから来ます。根拠の測定は `../archive/batch-effect/` にあります。

判定が揃ったら、`verify.py` が JSONL のフィールドと中項目の範囲と語の重複を検証します。そのうえで `finalize.py` が、複数のパスの判定から多数決で確定値を作り、確定しなかった語と落ちた語義を `review/` へ書き出します。`manifest.py` は生成の来歴を書き出し、そこには方針の全文と中項目の一覧、母集団の作り方とコマンドが入ります。確定値と来歴が揃えば、`build_release_table.py` が配布する表を書き、研究用の候補の表なら `build_table.py` が書きます。最後に `disagreement.py` が 2 つのモデルの確定値を突き合わせ、食い違う語を並べます。

## モジュール

入口のスクリプトは、共通の処理を次のモジュールから import します。

| モジュール | 役割 |
|---|---|
| `classifier.py` | 分類対象の定義にもとづく Signature と few-shot の実例の組み立て |
| `lm.py` | ゲートウェイを呼ぶ LM の組み立て |
| `jmdict.py` | JMdict の XML からの見出しの抜き出し |
| `corpus.py` | 評価コーパスの本文からの用例の切り出し |
| `load_target.py` | `--target` のフォルダにある分類対象の定義の読み込み |
| `votes.py` | 判定の保存形式の読み書き |

判定のフィールドの意味は `votes.py` の冒頭にあります。生成の方針のバージョン (`contract`)の上げ方は、各成果物の `votes/README.md` にあります。
